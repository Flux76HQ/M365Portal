## R-06: does libvips in the distroless image rasterise SVG?

**Yes.** The image carries sharp 0.35.5 with libvips 8.18.7 and librsvg 2.63.2. Evidence: (1) a direct `sharp(svgBuffer).png()` in a container started from the image (entrypoint override) gives a 128 by 128 PNG; (2) a real HTTP upload of a safe SVG to `POST /api/v1/branding/assets?slot=logoDark` answers 201 and the stored derivative is a PNG; (3) the hostile corpus H-01..H-44 (all the SVG fixtures: script, XXE, bombs, external references) passes against the container. Text in SVG does not render (no fonts, probe P22), which is why the monogram uses glyph paths; the icon check proves that path works in the image.

## Hostile corpus against the container

The harness of `apps/server/test/branding` (`viaHttp`, `runFixture`) was reused unchanged; only the target is different: a scratch vitest file starts one container per fixture (`--network host`, read-only rootfs, cap-drop ALL, `/data` and `/tmp` bind-mounted from the fixture workspace so that the "nothing left in /tmp or branding/.tmp" checks look at the right directories, the H-37 request-timeout preload mounted into the container), stops it with SIGTERM (exit code must be 0) and verifies the audit chain with the image's own `node dist/cli.js verify-audit`. Result on the final clean image: **44 of 44**. Earlier runs: 43 of 44 once (H-42 `body-9437185-bytes` expected 413 and saw a closed connection; it passed 3 of 3 alone and in the next full run; a race between the server closing the socket and the client reading the 413 while the machine was loaded, not an image defect). The harness lives in `scratchpad/s6b/hc/` and is **not** in the repository (see open point s6b-3).

## Open points for S6 (all also in `chunk-s6b.md`)

1. **VERSION label needs the build argument** (s6b-1, S7/S8): `image.yml` passes `VERSION`, so CI is fine; but the remediation texts of `image.yml` and any README that say `docker build -t m365portal:local .` produce an image whose version label is `unknown` and which the contents check and the smoke test refuse. They should say `docker build --build-arg VERSION="$(cat VERSION)" -t m365portal:local .`.
2. **`autoInstallPeers` puts type packages into the production tree** (s6b-2, S0/S1): `pnpm deploy --prod --legacy` ships `@types/better-sqlite3`, `@types/node` and `undici-types` (optional peers of drizzle-orm and sharp) and a link to the workspace package itself. The Dockerfile deletes them (and dangling links) after the copy; the cleaner fix would be `autoInstallPeers: false` or `peerDependencyRules.ignoreMissing`, which touches `pnpm-workspace.yaml` and the lockfile (not S6's file).
3. The size ceiling stays 400 MB (193.5 MB measured).
4. arm64, bridge mode, Trivy, SBOM, GHCR: GitHub only (above).
5. `docker build` for the first time takes about 1 to 2.5 minutes here; the sandbox needs `--build-arg HTTPS_PROXY="$HTTPS_PROXY"` (a predefined build argument, nothing in the Dockerfile) and the `extra_ca` secret.
