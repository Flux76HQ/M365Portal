# Chunk note s2g (T-A-092 to T-A-094): open points, assumptions, risks

Written by the `s2g` worker. Gate record: [`G2.md`](G2.md). For S8's consolidation (`T-A-278`).

## 1. Decisions the owner should know

1. **s2f-2 decided: an export with a missing master file stays a 500 `internal_error`, now deliberately.** A 409 says "the request conflicts with state the client can change"; the problem catalogue has 31 fixed codes and none fits (`staging_quota_exceeded` is the only 409), and a 409 tells an operator's monitoring that nothing is wrong while storage is damaged. Applied: `exportDocument` catches `AssetFileMissingError`, writes ONE audit row `branding.export` outcome `error`, reason `internal_error`, detail `{ schemaVersion: 1 }` (no hash, no path), and rethrows; the answer holds neither hash nor path, and no partial document is sent. Repairable from the UI: apply or reset drops the reference, then the export works. Test: `export-import.test.ts` "answers 500 internal_error when a master file is gone".
2. **Real bug found over real HTTP: the compression layer made the ETag of the branding documents weak, and the client's own `If-Match` was then refused (422 `invalid_etag`).** `compress.ts` (S1) turns every strong ETag into `W/"..."` when it compresses a body; the branding JSON is over 1 KiB, so a browser (which sends `Accept-Encoding`) reads `W/"1"`, sends it back and is refused; in-process tests never compress and never saw it. Fix in S2's files: `revisionHeaders(revision)` in `routes/request-support.ts` sets `ETag: "<n>"` and `Cache-Control: no-store, no-transform` on `GET`, `PUT`, `DELETE /api/v1/branding` and on a real import answer; `no-transform` is the opt-out `compress.ts` already honours. Test: `module.test.ts` "the ETag of the revision stays strong over a real connection that accepts gzip" (red first: `content-encoding: br`). Open point s2g-1 for S1/S5 (section 2).
3. **OpenAPI documents the contract's statuses.** The wrapper documented 403/413/415/422/429/500 only; the branding routes now also declare 409 (upload), 412 and 428 (apply, reset, import), 404 (asset) and 503 (all storage routes) with the problem schema (`PROBLEM_ANSWERS` in `request-support.ts`). `real-table.test.ts` compares every route with the status list of contract sections 4 and 5 (10 rows).
4. **Module shape.** `brandingModule(deps, options?)` (an optional second parameter, `{ images }`, lets a test pass a stand-in runner; `AppModuleFactory` callers pass `deps` only). `modules.ts`: one import and `[brandingModule]` (seam X1, nothing else changed). `start` does what chunk s2e section 2 lists, plus one call: `sweepTemporaryFiles` before registering the sweepers, so stale `.tmp` entries of a crashed process are gone before the first request (the hourly sweeper would only get them after the first run, which is asynchronous).
5. **`me` of the shell** is built in `module.ts` (`meOf`) from `resolveActor(deps.config, request)`, the catalogue order, `features.preview` only for the preview actor, `APP_VERSION`, `publicOrigin`, `deps.storageAvailable()`. It is a copy of the mapping in `routes/meta.ts` (S1 exports no builder; s2f-1). `module.test.ts` pins that the boot data `me` equals the `GET /api/v1/me` body for the anonymous and the preview actor.
6. **Table-driven tests over the real table** are in a new file of my territory, `test/branding/real-table.test.ts` (21 tests), not by editing `policy.test.ts` and `audit-integration.test.ts` (S1's files): the same assertions (anonymous 403 `permission_denied` with the handler never entered, no public write route, the preview actor gets past authorisation, every denial of every write route in five ways audited with the FR-A-034 fields, chain verifies without a gap, `branding.init` first) run over `buildApp` with the branding module, plus `assertRouteTable`, `assertRouterMatchesTable`, `assertOpenApiParity` and the 3.1 meta-schema over the real document. Negatives: a public write route, a document without the upload route, an application that audits nothing.
7. **The corpus over HTTP runs against the BUILT bundle as a process**, one fresh process and data directory per fixture (the staging quota of 32 files would otherwise fill up): `test/branding/hostile-built-server.ts` + the new describe block of `hostile-uploads.test.ts` (45 tests: 44 fixtures + the shape test). Each fixture also ends with `node dist/cli.js verify-audit` exit 0. Server settings for the test: `PREVIEW_MODE`, `PREVIEW_MODE_ALLOW_REMOTE`, `TRUST_PROXY=1`, `DATA_DIR` and `TMPDIR` of the fixture's workspace. Two accommodations, both outside the product: (a) the upload rate class allows one client 3 uploads in a burst, so `viaHttp` got an optional `clientAddress` that sends a distinct `X-Forwarded-For` per request (H-39's 20 simultaneous uploads and the multi-upload fixtures would otherwise be answered `rate_limited`, which is correct behaviour, not what the row tests); (b) H-37 needs a 1 s `requestTimeout` and the server's HTTP limits are deliberately constants, so the fixture preloads `test/fixtures/short-request-timeout.mjs` (`NODE_OPTIONS=--import=...`) that wraps `http.createServer` in that one process.
8. **Mutation check of the HTTP path**: emptying `AUDITED_REJECTIONS` in `assets-upload.ts` made H-14 and H-34 fail over the built server with "audit entries [] are not [branding.asset.stage:rejected]"; restored.
9. **Flaky test fixed (s2e's file, mine to fix):** `upload-pipeline.test.ts` "registers three sweepers ..." waited two turns of the event loop for an hourly sweep that does file I/O; it failed 2 of 3 runs on a busy machine. It now turns the loop until the sweep is seen (bounded at 5,000 turns, no sleeps).

## 3. Assumptions

- A1. The corpus over HTTP asserts one audit row per input with the actions of `expectedAudit`; `branding.init` is filtered out of the audit view (it exists once, from start).
- A2. `PREVIEW_MODE_ALLOW_REMOTE=true` in the corpus run is only there because the requests carry `X-Forwarded-For`; the preview actor is otherwise downgraded to anonymous by FR-A-036 (that downgrade is tested elsewhere).
- A3. The built bundle run needs `apps/server/drizzle/` next to `dist/` (the helper `buildLayout` lays it out like the image).

## 4. Risks

- R1. The per-fixture process makes the HTTP corpus take about 90 s on 4 shared CPUs (44 starts, each with a child process for the default row). Acceptable for CI; if it grows, share a server per group of fixtures whose uploads stay under the quota.
- R2. `no-transform` on the branding documents costs about 1.5 KB more per read on a connection that would have compressed it; the documents are read at page load and after a change only.
- R3. The preload that shortens the request timeout wraps `http.createServer` through `syncBuiltinESMExports`; a change in how `@hono/node-server` imports `http` would make H-37 fail loudly (the 408 would not come), not pass silently.
