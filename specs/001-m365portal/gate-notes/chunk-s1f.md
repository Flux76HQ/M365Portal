## 4. Assumptions and decisions

1. **A module is built from `ModuleDeps` by a factory** (`AppModuleFactory = (deps) => AppModule`), and `routes(deps)` gets the same object. C5 says `routes(deps)` and leaves the factory open; a factory with deps is what lets the branding module build its `ShellRenderer` from `deps.shellTemplate` and hold `deps.database` without a second channel. `start` is skipped in degraded mode (every step it stands for needs storage). A `start` that throws exits 1 and stops the modules that had started.
2. **`ModuleDeps.database()` is `undefined` in degraded mode and after the connection is closed**; `requireDatabase()` throws the `ProblemError` `storage_unavailable` (503). A module's routes that need storage call it; the denial audit of `buildApp` behaves the same way, so a denied write in degraded mode is the 503 and not the 403 (fail closed, nothing is written).
3. **The shell in degraded mode is the module's renderer too.** The renderer decides what to render with `deps.database() === undefined` (in-memory default branding, no icon links: `T-A-091`'s last test). The placeholder shell is used only when no module has a renderer.
4. **Readiness when the database is not there:** `database` fails with the cause (`database_unavailable` or `database_corrupt`, recorded at start) and `schema` fails with the same code, because a check can only fail with one of the four codes of the contract and the schema cannot be read. A checksum mismatch or a pending migration cannot exist after a successful start; if the files change under the running process, `schema` says `database_unavailable`. `database_corrupt` is sticky once the error handler has seen a corrupt-class storage failure (no automatic repair, E-10); any other storage failure only makes the next answer a fresh one.
5. **`storageAvailable` of `/api/v1/me` is `readiness.check().status === 'ready'`**, so it follows the same 2-second cache and flips with `/readyz`.
6. **Shutdown order:** stop accepting and close idle connections, stop the sweepers, run the modules' `stop` hooks (reverse order; this is where the image children are killed), drain up to 10 s while closing newly idle connections every 200 ms, cut what is left on a timeout (exit 1), then `wal_checkpoint(TRUNCATE)` and close the database. `Connection: close` is added by `buildApp.fetch` from the moment shutdown begins. A failing hook or a failing checkpoint is logged by step name and system code and does not change the exit code (the spec ties exit 1 to the drain timeout only).
7. **No `shutting_down` 503 for new requests during the drain.** The listening socket is closed first and idle connections are closed, so a new request can only arrive on a connection that was busy; it is answered normally and the connection is closed after it. `deps.isShuttingDown()` is available for the branding upload (`503 shutting_down`, S2).
8. **`healthcheck.ts` uses `node:http`, not `fetch`**, so that `HTTP_PROXY` and `NODE_USE_ENV_PROXY` (set in this sandbox) cannot send the check to a proxy. It asks `127.0.0.1` only; a `PORT` that is set and not a port in 1 to 65535 is exit 1, never the default.
9. **Logging at start:** every step writes `{event:'start_step', step}` at debug (that is how the order is proven from outside); `listening` carries the version and the port; `degraded`, `start_failed` (with a code, a module id or a route-table problem list: ids and paths, never values) and the shutdown events are fixed words. The posture line is unchanged (one line, no values).
10. **The build** (`build.mjs`) takes an optional `--outdir <dir>` (the lifecycle tests build into the scratchpad of the test, laid out like the image: `dist/`, `web/`, `drizzle/`, `node_modules`). The entries are `index`, `cli`, `healthcheck` and every `src/**/*-worker.ts` found by name; two workers with one file name stop the build. `splitting` is off on purpose: the image worker runs under Node's permission model and must be one file.
11. **The /healthz lint exemption is gone** (`LEGACY_HEALTH_ROUTE`, `isLegacyHealthRoute`, the three cases and the temporary-exemption test in `eslint-rules/test/no-direct-route-registration.test.ts`). The allowance for `new Hono()` in `apps/server/src/app.ts` stays as it was; `buildApp` no longer constructs one (`createHttpApp` does, in `route.ts`), so the rule's `APPLICATION_FILE` is now a hole that nothing needs (see open point s1f-6).
12. The fixture `test/fixtures/web-dist/sw.js` gained a `/* global self */` line; the static tests only look for the text `fixture service worker`.

## 6. Risks

- R1. **The drain test takes 10 real seconds** (`a request that outlives the 10 s drain is cut`): it is the only test that waits on a real clock, because the 10-second budget is a constant of `LIMITS` and the process is the unit. The in-process test of the same rule runs on the fake scheduler. On a very loaded machine the bounds (`>= 9.5 s`, `< 18 s`) could flake; they are generous on purpose.
- R2. **Ports.** The spawn tests pick a random free port in 18000-18999 and start the child at once; another process could take it in between (a collision is a failed test, not a wrong pass).
- R3. **`buildApp.fetch` copies a response whose headers are immutable** only when `Headers.set` throws; every response of this application is mutable today.
- R4. **A module that registers a route without `access`** is caught by the table check and exits 1 at start, as designed; the message lists route ids and paths, which are not secrets.
- R5. The bundle is built three times per full run (lifecycle, logging, version); each takes about a second.
