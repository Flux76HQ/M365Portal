## 3. Frozen interfaces (C4 to C7 and what G1 adds)

JSDoc of C4 to C7 was reviewed against the contracts: `http/route.ts` (C4), `module.ts` (C5, written in this chunk), `shell-port.ts` (C6), `audit/writer.ts`, `audit/chain.ts` and `db/tx.ts` (C7). No change was needed in C4, C6 or C7. The details of C4, C6 and C7 are in `chunk-s1e.md` section 4 and `G1a.md`/`chunk-s1d.md` section 4; they are frozen as written there. What this chunk adds:

- **C5 `module.ts`**: `AppModule { id; routes(deps); shell?; start?(ctx); stop?() }`, `AppModuleFactory = (deps: ModuleDeps) => AppModule`, `requireDatabaseOf(getter)`. `ModuleDeps { config, log, now, database(), requireDatabase(), storageAvailable(), webRoot, shellTemplate, sweepers: { register(sweeper) }, isShuttingDown() }`. `routes(deps)` receives the object the factory got. Order, everywhere: registration order in `appModules` (`src/modules.ts`, seam X1: **one line** appends the factory). `start` runs once, after the migrations, before the routes are built, **not in degraded mode**; a throw exits 1. `stop` runs at shutdown in reverse order, before the drain. The first module with a `shell` replaces the placeholder (also in degraded mode, where `database()` is `undefined`).
- **`app.ts`**: `buildApp(deps: BuildAppDeps): BuiltApp { fetch, http, shell }`. `BuildAppDeps { config, log, clock: ServerClock { now, monotonic }, readiness, database, modules, moduleDeps, webRoot, shellTemplate, shutdown: { isShuttingDown } }`. It builds the arguments of `createHttpApp` (CSRF on the wall clock, rate limiter on the monotonic one, the denial audit over `database()`, storage failures to `readiness.reportStorageFailure`, the core routes, the module routes, `[staticFallback, spaFallback]`) and adds `Connection: close` once shutdown has begun. `http.table` and `http.document` are what `writeRoutesOf` reads.
- **`start.ts`**: `startServer(options): Promise<RunningServer { server, port, storageAvailable, isShuttingDown(), stop(signal?) }>`, `StartError { code, exitCode }`, `installShutdownSignals(running, host?)`, `defaultWebRoot`, `defaultMigrationsFolder`. Options make the process injectable (`env`, `stderr`, `logDestination`, `modules`, `paths`, `clock`, `scheduler`, `umask`).
- **`lifecycle/`**: `createReadiness(options): ReadinessController { check(), reportStorageFailure(failure), storageAvailable() }`, `READINESS_CACHE_MS = 2000`; `createShutdown(options): { run(signal), isShuttingDown() }`, `checkpointAndClose(database)`, `ClosableServer`; `createSweeperRegistry(options): { register, start, stop }`, `SWEEP_INTERVAL_MS`, `Scheduler`, `systemScheduler`; `createStorageProbe(dataDir, io?)`, `ensureDataDir(dataDir)`.
- **`healthcheck.ts`**: `runHealthcheck(env, { timeoutMs? }): Promise<number>`; the script `node dist/healthcheck.js` exits 0 only on a 200 from `127.0.0.1:<PORT>/readyz` within 3 s.
- **Build** (`apps/server/build.mjs`): outputs `dist/{index,cli,healthcheck}.js` and `dist/<name>.js` for every `src/**/*-worker.ts` (`image-worker.js`), with maps; `--outdir <dir>`; `__APP_VERSION__` compiled in from the root `VERSION`; dependencies external, `@m365portal/shared` inlined; the build fails when anything of `node_modules` is inlined. Layout the start expects: `drizzle/` next to `dist/`, the web output in `web/` next to `dist/` or in `../../web/dist`.
- **Test helpers** for S2, S6 and S9: `test/helpers/built-server.ts` (`buildLayout`, `spawnServer`, `httpRequest`, `freePort`), `test/helpers/fake-scheduler.ts`, `test/fixtures/lifecycle-server.ts` (a module with a slow route, a storage route and a write route).
