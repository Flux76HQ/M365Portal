## 4. Interfaces the next tasks use

- `db` (import from `src/db/index.js`): `openDatabase({ path, foreignKeys?, readonly?, busyTimeoutMs? })` gives `{ sqlite, orm, path, close() }`; `databasePathOf(dataDir)`, `DATABASE_FILE_NAME`, `BUSY_TIMEOUT_MS`; the tables `branding`, `brandingAsset`, `auditLog` and their row types; `classifyStorageError` (`T-A-027`). `openDatabase` never creates the directory: a missing one is `SQLITE_CANTOPEN`, a file that is not a database `SQLITE_NOTADB` (`corrupt`), a directory in its place `SQLITE_CANTOPEN`. The busy timeout is the constructor option, not a PRAGMA (a PRAGMA takes no bound parameter and the lint rule forbids built SQL), and `db.test.ts` reads it back.
- `withTransaction(db, (tx) => ...)`: `BEGIN IMMEDIATE`, synchronous (a callback that returns a promise is refused and rolled back), a savepoint when nested through a `Tx`, refuses to start inside a transaction it did not begin. A `Tx` has `sqlite`, `orm` and **`afterCommit(callback)`**: runs after the outermost commit, discarded by a rollback of that transaction or of its savepoint, a callback that throws is ignored. `assertInTransaction(tx)` and `NotInTransactionError`.
- `db/migrate`: `await runMigrations(db.sqlite, { migrationsFolder, backupsDir, keepBackups?, log? })` returns `{ applied, schemaVersionBefore, schemaVersion, backupFile }` or rejects with `MigrationError { code, exitCode: 1 }` (`migration_checksum_mismatch`, `schema_newer_than_app`, `migration_journal_invalid`, `migration_files_unreadable`, `migration_backup_failed`, `migration_failed`, `migration_foreign_key_check_failed`, `migration_verification_failed`, `database_not_empty`). It switches foreign keys off and on itself, so the connection may have been opened either way. `inspectMigrations(appliedMigrations(db), shippedMigrations(folder))` is the read-only comparison (`current`, `pending`, `schema_newer_than_app`, `migration_checksum_mismatch`) that readiness can use. `migrateEmptyDatabase(db, folder)` is tooling for scratch databases. `db/backup`: `backupsDirOf(dataDir)`, `listBackups`, `takeBackup`, `pruneBackups`.
- `audit` (import from `src/audit/index.js`): `appendAudit(tx, entry)` returns `{ seq, hash }`. **The entry carries `ts`** (the injected clock's `iso()`): the writer has no clock of its own. Fields: `ts`, `actorKind` (`anonymous`, `preview`, `system`), `actorId`, `action` (route id or `entity.verb`), `targetType?`, `targetId?` (may be empty), `outcome`, `reasonCode?`, `clientIp?`, `requestId?`, `detail?` (the allow-list `AUDIT_DETAIL_KEYS`). Invalid input throws `AuditEntryError` (field names and issue codes, never a value) or `AuditDetailError` (key name only). `verifyChain(db, { from?, to? })`, `hashEntry`, `canonicalEntry`, `buildDetail`, `truncateUtf8`, `TRIGGER_NAMES`, `ZERO_HASH`, `setAuditHeadLog(log)` and `clearAuditHeadLog()`.
- `cli`: `runCli(argv, { env, stdout, stderr })` returns the exit code; the module runs itself when started as a script.

## 5. Assumptions and decisions

1. `CHECK` constraints, the partial index and `ON DELETE RESTRICT` are all emitted by `drizzle-kit generate` from `schema.ts` (the UNVERIFIED helper question of data-model section 4 is answered: `check()` and `index().where()` exist in 0.45.4). The hand-written section of `0000_init.sql` therefore holds only the three audit triggers, behind a banner. CHECK numbers are literals in `schema.ts`, not `LIMITS`, on purpose (a CHECK is part of the table as the migration made it).
2. SQLite reports an `ON DELETE RESTRICT` violation as `SQLITE_CONSTRAINT_TRIGGER` with the message `FOREIGN KEY constraint failed`, not as `SQLITE_CONSTRAINT_FOREIGNKEY`; either way it is not a storage failure for `db/errors.ts`, so it stays a 500 if it ever escapes.
3. The audit chain trigger runs BEFORE the CHECKs, so the 32-byte CHECK on `prev_hash` is unreachable without dropping the trigger. Both are kept (defence in depth); the test shows each.
4. `drizzle-kit` quirks that the scripts work around: `generate --out` with an absolute path is read as `./` plus the path and finds nothing (the drift check runs it with the scratch copy as the working directory), and its exit code is 0 even when it fails (the verdict comes from the output "No schema changes, nothing to migrate" and from the files written; a green drift check that did not run is therefore impossible, and the negative fixture proves a change is seen).
5. `drizzle-kit` formats `meta/*.json` its own way; `pnpm exec prettier --write` is run on them once at generation so that `prettier --check .` (S0's `format:check`) passes. A later `drizzle-kit generate` rewrites `_journal.json` and needs the same step.
6. A pending migration whose `when` is not newer than the newest applied one is `migration_journal_invalid` (it would be skipped silently, P13). A journal `when` moved EARLIER than an applied row reads as `schema_newer_than_app`, one moved LATER as `migration_checksum_mismatch`: PD-06's rule applied literally; both are asserted.
7. If the pre-migration backup cannot be written, nothing is migrated (`migration_backup_failed`). FR-A-064 is a SHOULD, but proceeding without the copy would defeat its point.
8. `verify-audit` exits 1 when the chain is broken OR an append-only trigger is missing (the JSON says which), 0 only when both are fine, 2 when it could not check. The tasks text says "exits 1 when not ok"; a database whose triggers were dropped is what someone who edited the log leaves behind, so it is not reported as healthy. `verifyChain` itself keeps `ok` for the chain alone and reports `triggersMissing` beside it, as data-model 7.3 has it.
9. `firstBadSeq` is the seq of the first row that fails. For a deleted row that is the row after the gap. Rows lost from the END and a chain recomputed from the first changed row on are not detected, and two tests assert exactly that, so the documented limit cannot drift.
10. The head is logged after the commit through `tx.afterCommit`, not inside `appendAudit` before the commit: a logged head that was rolled back would be a false anchor. The sink is registered once with `setAuditHeadLog` because the callers of `appendAudit` have no logger.
11. The detail allow-list is my reading of data-model 7.4: the keys are listed in `canonical.ts` (`compact` and `logoCompact` are both allowed because the contract names the upload slot `compact` and the branding role `logoCompact`). A string array keeps 16 items; a null value is refused; an `undefined` value is absent.
12. `ts` is a required field of the entry. Alternatives (a registered clock) would have added a second source of time next to the injected one.
13. A worker thread does not inherit tsx: `--import tsx` in `execArgv` is accepted and does nothing there, and the worker then loads the `.ts` file with Node's own type stripping and fails on `./writer.js`. `test/helpers/audit-worker-entry.mjs` registers tsx's hooks (`tsx/esm/api`) and imports the worker.

## 7. Risks

- R1. `better-sqlite3` on arm64 and on the distroless runtime was not executed here (stack probe section 8 still stands); the module loads on linux-x64 glibc and the WAL works on a temporary directory of this sandbox, not on a bind-mounted volume.
- R2. The concurrency test uses five worker threads that open their own connections. They overlap in time only as far as the scheduler lets them; the test cannot prove that two of them really asked for the lock together. What proves the mechanism is the pair of controls (a deferred writer loses to `SQLITE_BUSY_SNAPSHOT`, the trigger refuses a repeated seq) and the lock probe inside `appendAudit`'s transaction. The worker test takes 3 to 6 s on a loaded machine (tsx compiles in each worker).
- R3. `verify-audit` opens the database read-only; on a WAL database that needs write access to the directory for the `-shm` file unless the writer's files exist. In the container the same uid owns the volume, so it works; run beside a live server it reads a consistent snapshot. Not tested against a volume with different ownership.
- R4. The synthetic fixtures duplicate the audit DDL of migration 0000 (about 40 lines in three folders). They are static on purpose; `migrations.upgrade.test.ts` checks that the good ones regenerate from their own migrations, so a typo is caught, but a future change to the real audit DDL does not flow into them.
- R5. The seed of version 0 for the real schema and the synthetic seeds are my construction of "rows an older version would leave". They satisfy every constraint of the schema (asserted), not the full range of real data.
