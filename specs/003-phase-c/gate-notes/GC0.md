## Decisions taken while building

- **Fragments are the source.** `locales/lazy/{users,groups}.*.json` are generated by `pnpm i18n:merge` from `i18n/fragments/{users,groups}.{en,nl}.json`; tasks.md names the lazy files, the hand-edited files are the fragments. S-C3 fills the fragments (T-C-047) and runs the merge.
- **New owner `SC3`** in `NAMESPACE_OWNERS` for `users` and `groups` (the merge script's owner union gained the member; two ownership tests were extended, not weakened).
- **`./directory/*` is a new subpath of `@m365portal/shared`.** The territory of S-C1 includes `src/directory/**`; without an `exports` entry nobody can import it. `package.json` and the frozen-map test (`exports.test.ts`: expected map, no barrel, three negatives) carry it. This is a decision of S0 in Phase A terms; recorded here as the amendment.
- **Detail code message key** `graph_permission_missing` is `users.error.graph_permission_missing` (EC-C14, pointing to Settings, Connection). Both directory pages must load the `users` namespace for it (S-C3 note for T-C-042/T-C-044).
- **`groupKindOf`**: `Unified` in `groupTypes` decides `m365` on its own (the same predicate as the list filter, so a row the `m365` filter returns is never labelled differently); `null` or a malformed value of any of the three properties gives `unknown`; so does "neither mail nor security". It also exports `membershipTypeOf` (`assigned` / `dynamic`, FR-C-304), `READ_ONLY_GROUP_KINDS`, `isReadOnlyGroupKind`.
- **Shell content.** `users`: `error.graph_permission_missing`, `manager.none`, `manager.unavailable`, `restricted.row`. `groups`: `kind.{m365,security,mailsecurity,distribution,unknown}`, `members.hidden`, `members.restricted` (one/other), `owners.notAvailable`. Everything else is T-C-047.
- **Defaults in query schemas.** `enabled`, `type`, `kind` default to `all` and `order` to `asc` (Zod defaults, no transform), so a parsed query always has them; `q`, `limit`, `cursor` stay optional (`limit` is text, as in `PageQuerySchema`).

## Open points, assumptions, risks, UNVERIFIED

- **Not in the wire contract: membership rules of dynamic groups.** FR-C-304 says "membership rules are shown as text for dynamic groups" but its field list has no `membershipRule`, and FR-C-104 caps text at 256 bytes (a rule can be longer, so a truncated rule would mislead). Left out; `membershipType` says `dynamic`. A later amendment may add a field once Learn is read for the property length (not read in Phase C research; not verified).
- The manager of a user is a `DirectoryRow` (restricted when out of scope): S-C2 must run it through `restricted-rows.ts`; S-C3 must render a restricted manager.
- A user shown through a `basic` grant in members/owners has `userPrincipalName: null` (the projection never reveals it).
- `createdDateTime` on the wire is `YYYY-MM-DDTHH:mm:ss.sssZ`; Graph sends it without milliseconds, so the mapper must normalise (`toISOString`).
- The users/groups lists do not expose a restricted row; P35 omits groups the actor cannot see (PC-05), enforced by the schema (no restricted row in `UserGroupsResponse`).
- `LIMITS.directory.pageLimitDefault/Max` equal `PAGE_LIMIT_DEFAULT/MAX` of `schemas/common.ts` (a test ties them); the spec's "UI asks for 50" is a web constant, not a limit.
- UNVERIFIED: that `pnpm install --frozen-lockfile` on a clean copy, `pnpm build` and `pnpm bundle:check` stay green (no entry or dependency change; the two namespaces are lazy chunks). Run by T-C-069.
