# Research: Microsoft facts for Phase D (Exchange Online recipients: distribution groups and mail contacts)

Date of reading: 2026-10-13 (Microsoft Learn, Exchange Online PowerShell module, Graph v1.0). Same rules as `specs/003-phase-c/research-microsoft-c.md`: every row names the page, what it says and what the spec does with it. A statement Learn does not make is not a fact here; it is an UNVERIFIED row, numbered `U75` and up (U1 to U74 are taken, see `docs/open-points.md`). Nothing below comes from memory. Verdict per question: VERIFIED (Learn states it), UNVERIFIED (Learn does not state it, or only part of it). CSV or formula injection is not a Microsoft topic and is skipped (question 5).

Context: Phase D adds writes through Exchange Online PowerShell (`pwsh`) with app-only (certificate) authentication, because Graph cannot manage distribution groups, mail-enabled security groups or mail contacts (Phase C, R-C-04).

## R-D-01 App-only authentication from PowerShell (question 1)

Pages: https://learn.microsoft.com/powershell/exchange/app-only-auth-powershell-v2 and https://learn.microsoft.com/powershell/module/exchangepowershell/connect-exchangeonline

- VERIFIED. `Connect-ExchangeOnline` supports three certificate forms, all with `-AppId` and `-Organization` (the primary `.onmicrosoft.com` domain): `-CertificateThumbprint`, `-Certificate <X509Certificate2>`, `-CertificateFilePath` plus `-CertificatePassword` (SecureString). The three are mutually exclusive.
- VERIFIED. `-CertificateThumbprint` "is supported only in Microsoft Windows" (cmdlet page, and the app-only page: the certificate must sit in the user certificate store). So it is not usable in a Linux container.
- VERIFIED. `-Certificate`: "The certificate doesn't need to be installed on the computer ... You can store the certificate object remotely. The certificate is fetched when the script is run." The cmdlet page example says it suits certificates "stored in remote machines and fetched at runtime", Azure Key Vault named as the example. This is the documented route for "no private key on disk".
- VERIFIED. `-CertificateFilePath` needs a file path (a `.pfx` on disk) and a password; the page itself says "there's really no automated and secure way to connect using a local certificate". So the file route is the one the spec avoids.
- VERIFIED. Minimum module version for certificate authentication in `Connect-ExchangeOnline`: 2.0.4 or later.
- VERIFIED. Windows-only caveat: CNG certificates "aren't supported for app-only authentication"; a CSP key provider certificate is needed (the page words it for Windows PowerShell certificates; the requirement for the .NET object on Linux is not stated, see U75).
- VERIFIED. Entra roles supported for Exchange Online PowerShell app-only (option 1, table): Compliance Administrator, **Exchange Administrator**, **Exchange Recipient Administrator**, Global Administrator, Global Reader, Helpdesk Administrator, Security Administrator, Security Reader. The page says Global Administrator and Exchange Administrator "provide the required permissions for any task in Exchange Online PowerShell", recipient management named. These roles cannot be customised or scoped.
- VERIFIED. Option 2 is a custom Exchange role group: `New-ServicePrincipal -AppId -ObjectId -DisplayName`, then `Add-RoleGroupMember`; recommended "to restrict the available commands" and "to use a Write scope to limit which recipients can be modified". Option 3 combines Entra roles with custom role groups (RBAC combines all sources); the page names extending Exchange Recipient Administrator as an example.
- VERIFIED. API permission: resource "Office 365 Exchange Online" (app id `00000002-0000-0ff1-ce00-000000000000`), application role `Exchange.ManageAsApp` (id `dc50a0fb-09a3-484d-be87-e023b12c6440`), admin consent required and to be granted. The page also says to revoke the default `Microsoft Graph > User.Read` consent.
- VERIFIED. Not supported with app-only authentication in Exchange Online PowerShell: the Microsoft 365 Group cmdlets `New-UnifiedGroup`, `Remove-UnifiedGroup`, `Add-UnifiedGroupLinks`, `Remove-UnifiedGroupLinks`; the page points to Microsoft Graph. So Microsoft 365 Group membership stays on Graph (`GroupMember.ReadWrite.All`, granted in Phase B).
- VERIFIED. The module stores a temporary copy of itself locally (`-EXOModuleBasePath`, module 3.9.1-Preview1 or later; default the temp folder, stated for Windows as `%TMP%`). That is the module, not the key.
- UNVERIFIED (U75). Learn does not say that `-Certificate` with an X509Certificate2 built in memory (from PFX or PEM bytes held by the process) works in PowerShell 7 on Linux, nor that no key material is written to disk by the module or its token library. The module is supported on Linux (R-D-03) and the parameter is documented without a platform restriction, but "works on Linux with an in-memory key" is not stated.
- UNVERIFIED (U76). Whether Exchange Recipient Administrator is enough for every Phase D cmdlet (`Add-`/`Remove-DistributionGroupMember`, `New-`/`Set-`/`Remove-MailContact`, the `Get-` cmdlets). The table lists the role as supported; per-cmdlet permissions are found with `Find-the-permissions-required-to-run-any-Exchange-cmdlet` (https://learn.microsoft.com/powershell/exchange/find-exchange-cmdlet-permissions), not read. Exchange Administrator is documented as sufficient for recipient management.
- UNVERIFIED (U77). `Exchange.ManageAsAppV2`: no Learn page read or found by search names this role. Only `Exchange.ManageAsApp` is documented. The spec uses `Exchange.ManageAsApp` and does not depend on a V2 role.
- Used by: the Phase D connection design (certificate from memory, `-Certificate`), the application permission list, owner test OV-D1.

## R-D-02 Distribution groups and mail contacts: cmdlets and semantics (question 2)

Pages: https://learn.microsoft.com/powershell/module/exchangepowershell/add-distributiongroupmember, .../get-distributiongroup, .../get-distributiongroupmember, .../get-dynamicdistributiongroupmember, .../get-recipient, .../new-mailcontact, .../set-mailcontact, .../remove-mailcontact, https://learn.microsoft.com/exchange/recipients-in-exchange-online/manage-mail-contacts, https://learn.microsoft.com/powershell/exchange/recipient-filters, https://learn.microsoft.com/powershell/exchange/filter-properties

- VERIFIED. `Get-DistributionGroup` "view[s] existing distribution groups or mail-enabled security groups"; it has `-Filter`, `-ResultSize <Unlimited>`, `-SortBy`, `-RecipientTypeDetails`, `-ManagedBy` (own parameter set), `-IncludeManagedByWithDisplayNames`. `Get-DistributionGroupMember` takes `-Identity` and `-ResultSize`. Members of **dynamic** distribution groups are read with `Get-DynamicDistributionGroupMember`, whose result "is updated every 24 hours"; the dynamic group itself is `Get-DynamicDistributionGroup`, and its membership "is recalculated whenever an email message is sent to the group".
- VERIFIED. `Add-DistributionGroupMember` "add[s] a single recipient to distribution groups and mail-enabled security groups". `-Member` accepts name, alias, DN, canonical DN, email address or GUID. Supported member types: `UserMailbox`, `SharedMailbox`, `RoomMailbox`, `EquipmentMailbox`, `MailUser`, `MailContact`, `MailUniversalDistributionGroup`, `MailUniversalSecurityGroup`. **Not** supported as members: Microsoft 365 groups and non-mail-enabled Entra users. (`Remove-DistributionGroupMember` was not read; its sibling shape is assumed only in U78.)
- VERIFIED. `-BypassSecurityGroupManagerCheck`: "If you aren't defined in the ManagedBy property of the group, you need to use this switch in commands that modify or delete the group." Using the switch needs, for distribution and mail-enabled security groups, membership of the Organization Management role group or the Security Group Creation and Membership role. Ownership is the `ManagedBy` property of the group.
- VERIFIED. `Get-Recipient` returns all mail-enabled objects (mailboxes, mail users, mail contacts, distribution groups). In Exchange Online the page recommends `Get-EXORecipient` instead. Microsoft 365 groups need `-RecipientTypeDetails GroupMailbox`. It "might not return all object-specific properties": use the type cmdlet (`Get-MailContact`, `Get-DistributionGroup`) for those.
- VERIFIED. Mail contacts: `New-MailContact` has `-Name` and `-ExternalEmailAddress` as mandatory parameters (syntax block), optional `-Alias`, `-DisplayName`, `-FirstName`, `-LastName`, `-PrimarySmtpAddress`. `Set-MailContact` changes mail properties (`-ExternalEmailAddress`, `-Alias`, `-DisplayName`, `-Name`, `-CustomAttribute1` to `15`, `-HiddenFromAddressListsEnabled`, `-MailTip`, ...). `Remove-MailContact` takes `-Identity`, `-Confirm`, `-WhatIf`. Organisation properties (title, department, company, manager) are `Set-Contact`, not `Set-MailContact`; `Get-Contact -Filter` exists.
- VERIFIED. Destructive cmdlets (`Remove-*`) pause for confirmation; `-Confirm:$false` skips it. Relevant for a non-interactive worker.
- VERIFIED. OPATH filter syntax: the whole filter in double quotes (single quotes when it holds `$true`, `$false`, `$null`); operators with a hyphen: `-and -or -not -eq -ne -lt -gt -like -notlike`; `-eq` is not case-sensitive; wildcards only with `-like` and only on text properties; in Exchange Online "the wildcard character is supported only as a suffix in most parameters" (`'sales*'` yes, `'*sales'` no); blank values with `$null`. A property is filterable only on the cmdlets listed in its section of the filter-properties page (otherwise "not a recognized filterable property"). Properties that link to another object (such as `ManagedBy`) hold the object's DN, so a name or address "don't match anything" (stated on the RecipientFilter page; the `-Filter` page lists `AcceptMessagesOnlyFrom` the same way). The spec escapes every value placed in a filter (single quote doubled) or avoids `-Filter` and filters in the panel.
- VERIFIED. Bulk limit: "Cmdlets backed by the REST API have a 15-minute timeout, which can affect bulk operations", the page's example being `Update-DistributionGroupMember` on 10,000 members. `Add-DistributionGroupMember` is one recipient per call.
- VERIFIED (partial). Groups synced from on-premises are managed on-premises: "Distribution groups that are created in Microsoft 365 through directory synchronization must be managed in the on-premises environment" (https://learn.microsoft.com/troubleshoot/exchange/groups-and-distribution-lists/cannot-manage-dg), error text "The action '<cmdlet>', '<property>', can't be performed on the object '<name>' because the object is being synchronized from your on-premises organization." This is the read-only-in-the-cloud rule for groups. The page does not mention mail contacts.
- VERIFIED. Mail users: "When you create mail users in Exchange Online PowerShell, you might encounter throttling" (https://learn.microsoft.com/exchange/recipients-in-exchange-online/manage-mail-users). The same sentence is not on the mail contacts page.
- UNVERIFIED (U78). Whether a service principal that holds an Entra role (Exchange Administrator) and is not in any `ManagedBy` list must pass `-BypassSecurityGroupManagerCheck`, and whether that role satisfies "Organization Management or Security Group Creation and Membership". Learn gives the rule for a user account; it says nothing about the app-only principal. Plan: send the switch on every write the panel authorises itself, and check ownership in the panel first; owner test OV-D2.
- UNVERIFIED (U79). Default result size and paging of the PowerShell cmdlets. The cmdlet pages read show `-ResultSize` with "Default value: None" and no description of a default; no `-Skip` or page token exists on them. The only stated default (1,000, with `@odata.nextLink`) is for the Exchange Online Admin API endpoint of `Get-DistributionGroupMember` (https://learn.microsoft.com/exchange/reference/admin-api-endpoints-distribution-group-member), a different surface, and `Get-EXO*` cmdlets have `-PageSize` 1 to 1000, default 1000 (connect page). The spec asks for `-ResultSize Unlimited` and pages in the panel (in memory), and does not rely on a default.
- UNVERIFIED (U80). How to detect "synced from on-premises" per object (property name such as `IsDirSynced`) and whether mail contacts synced from on-premises also reject cloud writes with the same error. Not on any page read.
- UNVERIFIED (U81). Numeric throttling limits of Exchange Online PowerShell for an app-only principal (budget, concurrent sessions, requests per time). Learn says throttling exists (R-D-04) and gives numbers only for other surfaces (Message trace V2: 100 requests per 5 minutes per tenant; EWS; SMTP), which do not apply.
- UNVERIFIED (U82). The delay between a successful write (`Add-DistributionGroupMember`, `New-MailContact`) and a correct read-back through `Get-DistributionGroupMember`, `Get-MailContact` or Graph. Learn states a replication delay for Graph group lists (R-C-03) but nothing for Exchange Online cmdlets. The spec treats a read right after a write as possibly stale and shows the cmdlet's own success as the result.
- Used by: Phase D read and write requirements for distribution groups, mail-enabled security groups and mail contacts; the ownership check; the "read-only because synced" rule; filter escaping.

## R-D-03 PowerShell and the module on Ubuntu 24.04 LTS (question 3)

Pages: https://learn.microsoft.com/powershell/exchange/exchange-online-powershell-v2, https://learn.microsoft.com/powershell/scripting/install/install-ubuntu?view=powershell-7.6, https://learn.microsoft.com/powershell/scripting/install/linux-overview?view=powershell-7.6, https://learn.microsoft.com/powershell/scripting/install/alternate-install-methods?view=powershell-7.6

- VERIFIED. The module is "officially supported in PowerShell 7 on Windows, Linux, and Apple macOS". Ubuntu 24.04 LTS table: module 3.10.0 or later needs PowerShell 7.6.0 or later (.NET 10); 3.5.0 to 3.9.2 needs 7.4.0 or later (.NET 8); 3.0.0 to 3.4.0 needs 7.2.0 to 7.3.7. Ubuntu 24.04 support ends 2029-05-31.
- VERIFIED. Linux limits: `Connect-IPPSSession` (Security & Compliance PowerShell) is not available on Linux; behind a proxy server the module must be 3.0.0 or later (the panel does not use Security & Compliance PowerShell).
- VERIFIED. Install PowerShell: preferred route is the Microsoft package repository (`packages.microsoft.com`) with the registered repository package, `apt`; PowerShell 7.6 is marked LTS; alternatives are the `.deb` from GitHub releases and a `tar.gz` binary archive (dependencies to be installed by hand). `pwsh` starts it; installed under `/opt/microsoft/powershell/7/`; shared modules `/usr/local/share/powershell/Modules`, user modules `~/.local/share/powershell/Modules`. Ubuntu's own repository has different .NET packages, which can clash with the Microsoft one (package mix-up page); choose one feed.
- VERIFIED. The module comes from the PowerShell Gallery: `Install-Module ExchangeOnlineManagement` (`-Scope CurrentUser` or all users, `-RequiredVersion` to pin). PowerShell 7 already uses TLS 1.2 or later for the Gallery.
- VERIFIED. All cmdlets use REST API connections "since 2023"; the REST connection avoids a PowerShell runspace; `-UseRPSSession` is deprecated from module 3.9.2. REST connections "require the PowerShellGet and PackageManagement modules" (the page's section title says "in Windows"; PowerShell 7 ships PowerShellGet).
- VERIFIED. Efficiency options: `-CommandName` imports only the listed cmdlets ("improve performance and reduces the memory footprint"); `-SkipLoadingFormatData` "run[s] Connect-ExchangeOnline commands faster"; cmdlet help files are no longer downloaded by default from 3.7.0-Preview1 (`-LoadCmdletHelp` to get them); `-ShowBanner:$false` hides the banner. `Get-ConnectionInformation` (3.0.0 or later) shows the connections.
- VERIFIED. "Frequent use of the Connect-ExchangeOnline and Disconnect-ExchangeOnline cmdlets in a single PowerShell session or script might lead to a memory leak. The best way to avoid this issue is to use the CommandName parameter." This bears on the worker design: connect once and reuse, not connect per call in a long-lived process.
- VERIFIED. The .NET SDK container images contain PowerShell; Microsoft says they are for testing and that a production image must be built and maintained by the owner of the workload.
- UNVERIFIED (U83). The first module version with REST for every cmdlet (Learn says "since 2023" and ties REST to the V3 module; no version number stated), and therefore the lowest version the panel may pin. The spec pins an exact version that matches the PowerShell version (R-D-03 table) and records it.
- UNVERIFIED (U84). Image size added by PowerShell plus the module, startup time of `pwsh`, time of `Connect-ExchangeOnline`, and resident memory of a warm session. Learn gives no figures. Measure in the owner test OV-D1 and in the build.
- UNVERIFIED (U85). Lifetime of an app-only `Connect-ExchangeOnline` session in a long-lived `pwsh` process: whether the module renews the token itself, after how long the session needs a new `Connect-ExchangeOnline`, and the effect of idle time. Learn only states the memory-leak tip, the 15-minute timeout per REST cmdlet and the built-in retry of transient failures. The worker design (one long-lived process versus one process per call, restart after N calls or on error) therefore rests on measurement, not on Learn.
- Used by: the container/image decision, the worker model, the version pin.

## R-D-05 Certificate self-rotation through Graph (question 4)

Pages: https://learn.microsoft.com/graph/api/application-addkey, https://learn.microsoft.com/graph/api/application-removekey, https://learn.microsoft.com/graph/application-rollkey-prooftoken, https://learn.microsoft.com/entra/identity/enterprise-apps/tutorial-enforce-secret-standards, https://learn.microsoft.com/entra/identity-platform/how-to-add-credentials

- VERIFIED. `POST /applications/{id}/addKey` and `POST /applications(appId='{appId}')/addKey`: "can be used by an application to automate rolling its expiring keys", together with `removeKey`. Body: `keyCredential` (`type` `AsymmetricX509Cert` with `usage` `Verify`, and `key`, the base64 public certificate; `X509CertAndPassword` needs `Sign` and a `passwordCredential`), `passwordCredential` (null for the first type) and `proof`. Response `200 OK` with the new `keyCredential`. "You should only provide the public key value when adding a certificate credential."
- VERIFIED. `POST /applications/{id}/removeKey`: body `keyId` (GUID) and `proof`; response `204 No Content`.
- VERIFIED. Permissions: application least privileged `Application.ReadWrite.OwnedBy`; higher `Application.ReadWrite.All`, `Directory.ReadWrite.All`. And, on both pages: "An application doesn't need any specific permission to roll its own keys." So the panel's application needs no new Graph permission to rotate its own certificate (Phase B holds none of the three).
- VERIFIED. Proof of possession: a self-signed JWT signed with the private key of one of the application's **existing valid** certificates; claims `aud` = `00000002-0000-0000-c000-000000000000`, `iss` = the application that initiates the request, `nbf`, and `exp` = `nbf` + 10 minutes (recommended lifespan 10 minutes). The Key Vault note: the padding character `=` must not be in the JWT header and payload, otherwise `Authentication_MissingOrMalformed`.
- VERIFIED. "Applications that don't have any existing valid certificates (no certificates have been added yet, or all certificates have expired), won't be able to use this service action." They must use Update application (`PATCH /applications/{id}` with `keyCredentials`) with a permission or a user. So rotation has to happen **before** the current certificate expires; after expiry the owner repairs it by hand.
- VERIFIED. Rolling order the pages imply: addKey (new public certificate, proof signed by the old key), switch the panel to the new key, then removeKey (old `keyId`, proof signed with a valid key). The same two actions exist on `servicePrincipal`.
- VERIFIED. Validity caps: Learn states a **client secret** maximum of 24 months (recommended under 12). For certificates, Learn describes an optional tenant **app management policy** that can cap certificate lifetime (the tutorial recommends 180 days; a Q&A shows the error "Credential lifetime exceeds the max value allowed as per assigned policy"). The tenant owner can therefore impose a cap, and the panel must read the failure and report it.
- UNVERIFIED (U86). Which identifier goes in `iss` of the proof: the addKey page says "the ID of the application"; the proof-token page says the application or service principal "object" and its sample passes the **object id** (`objectId`) to the proof generator while using the client id for the client assertion. Whether the object id or the app (client) id is required is ambiguous. Test in OV-D3; the code can try the object id first (as in the sample).
- UNVERIFIED (U87). A fixed one-year cap on certificate validity, and a maximum number of `keyCredentials` per application. Neither is stated on the pages read: the only caps documented are the optional policy (180 days recommended) and the 24 months for secrets. The panel generates a certificate valid for the shorter of 1 year and what the policy allows, and treats a rejection as a reportable error.
- UNVERIFIED (U88). How soon after `addKey` a token request and `Connect-ExchangeOnline` with the new certificate succeed (propagation), and whether Exchange Online accepts the new certificate at once. Learn is silent. The panel keeps the old key until the new one has authenticated once (verify before `removeKey`).
- Used by: certificate lifecycle in Phase D (rotation job, expiry warning, break-glass path), owner test OV-D3.

## R-D-06 Audit of changes made through app-only cmdlets (question 6)

Pages: https://learn.microsoft.com/purview/audit-log-activities#exchange-admin-activities, https://learn.microsoft.com/purview/audit-search, https://learn.microsoft.com/powershell/module/exchangepowershell/search-unifiedauditlog, https://learn.microsoft.com/powershell/module/exchangepowershell/search-adminauditlog

- VERIFIED. "Exchange administrator audit logging (which Microsoft 365 enables by default) logs an event in the audit log when an administrator (or a user assigned administrative permissions) makes a change in your Exchange Online organization ... by using the Exchange admin center or by running a cmdlet in Exchange Online PowerShell." Cmdlets beginning with `Get-`, `Search-` or `Test-` are not recorded.
- VERIFIED. "Some Exchange Online cmdlets aren't logged ... Many of these relate to maintaining the Exchange Online service." Reading the audit entry shows "what cmdlet was run, which parameters and parameter values were used, and what objects were affected" (export of results).
- VERIFIED. Search: `Search-UnifiedAuditLog -RecordType ExchangeAdmin`; "it might take up to 30 minutes after an Exchange cmdlet is run" for the entry to appear (audit-log-activities); core-service records are "typically 60 to 90 minutes" with no committed time (audit-search). `Search-UnifiedAuditLog` returns up to 100 records by default; `-SessionCommand ReturnLargeSet` up to 50,000 (unsorted); for programmatic collection Microsoft recommends the Office 365 Management Activity API. Audit (Standard) retention is 180 days for logs from 2023-10-17.
- VERIFIED. `Search-AdminAuditLog` "has been deprecated in the cloud-based service" and is on-premises only; use `Search-UnifiedAuditLog`.
- UNVERIFIED (U89). That a cmdlet run by an **application** (service principal) in app-only mode is recorded in the Exchange admin audit log, and which value identifies it (user id field, app id). The page speaks of "an administrator (or a user assigned administrative permissions)". Owner test OV-D4 (run one write, search for it).
- UNVERIFIED (U90). That each specific Phase D cmdlet (`Add-`/`Remove-DistributionGroupMember`, `New-`/`Set-`/`Remove-MailContact`) is in the logged set (Learn says some are not logged and gives no list). Same test.
- Spec consequence: the panel keeps its own audit record of every write (who, what, target, result) and does not depend on the Exchange log; the Exchange log is a second source the owner can cross-check, and the panel audit may name it as a reference (`Search-UnifiedAuditLog -RecordType ExchangeAdmin`, delay up to 30 minutes).

### R-D-08 Graph: add and remove a group member

- VERIFIED. `POST /groups/{group-id}/members/$ref` with a JSON body `{ "@odata.id": "https://graph.microsoft.com/v1.0/directoryObjects/{id}" }` and `Content-type: application/json`; success is `204 No Content`. Supported only for security and Microsoft 365 groups. A user can be a member of both; a security group can also hold security groups, devices, service principals and organizational contacts; a Microsoft 365 group cannot be a member of any group.
- VERIFIED. Errors: `400 Bad Request` "when the object is already a member of the group, is unsupported as a group member, or when the group was recently created and hasn't fully replicated" (message "The source resource object or one of the objects being referenced don't exist.", retry after a brief delay); `404` when the object being added does not exist; `403` for a group that cannot be managed through Graph (this API supports only security and Microsoft 365 groups), for a member type the caller lacks permission for, or for a role-assignable group without `RoleManagement.ReadWrite.Directory`.
- VERIFIED. Application permission for a user member: `GroupMember.ReadWrite.All` (the same for group members). Adding devices, service principals and org contacts needs further permissions (`Device.ReadWrite.All`, `Application.ReadWrite.All`, `OrgContact.Read.All`); Phase D adds users only. Role-assignable groups additionally need `RoleManagement.ReadWrite.Directory`, which the panel does not hold: such a group answers 403 and the panel maps it to `permission_denied` for the group, not to a missing panel role.
- VERIFIED. Bulk: `PATCH /groups/{group-id}` with `members@odata.bind` takes up to **20** members; "If an error condition exists in the request body, no members are added". So the bulk form is all-or-nothing and gives no per-member result. This is why `LIMITS.groupMembers.chunk` is 20 and the contract is one `$ref` call per member (plan 5.3 stands; the PATCH form is not used).
- VERIFIED. `DELETE /groups/{id}/members/{id}/$ref`, no request body, `204 No Content`. **Caution on the page**: without `/$ref` the member object itself is deleted from Entra ID when the app may manage that object type (an app with `GroupMember.ReadWrite.All` and `User.ReadWrite.All` would delete a user). The panel holds no `User.ReadWrite.All`, but the client must still build the path only through one function that always appends `/$ref`, with a test that fails on a path without it. You cannot remove a member from a group with dynamic membership.
- UNVERIFIED (U92). How to tell "already a member" from "unsupported member type" or "not replicated yet": all three are `400`, the page gives one message text for the replication case only.
