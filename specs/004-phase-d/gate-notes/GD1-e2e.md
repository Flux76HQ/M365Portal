## How the topology gives the server a `pwsh` (task 1)

`servers.ts`: `makePwshShimDirectory(runDir)` makes `<runDir>/pwsh/` with a link `pwsh` to `e2e/support/pwsh-shim/pwsh` and a link `node` to `process.execPath`; `global-setup.ts` calls it before the servers start; `spawnInstance` puts that directory first on the `PATH` of instance A only (B reaches Exchange only through the wizard's REST probe). Nothing under `apps/` knows about it: the product's own `resolveCommand` finds the file. The credential path is the real one: the key the wizard sealed is handed to the worker as PEM and the stand-in refuses a key that does not belong to the certificate, so every Exchange answer in these specs also proves that path (it worked on the first run).

`support/exchange-seed.ts` writes `seed.json` next to the link (the stand-in re-reads it on every request): `seedExchange(seed = standardSeed())` is the reseed between tests, `clearExchangeSeed()` ends a spec. The standard seed: five users that ARE the principals of the fake directory (same object id, same address, so the member rows and the picker match Graph), three contacts (one synchronised), five lists (Marketing, Sales, Archive empty, Legacy synced, Everyone dynamic). A seed is made different from the one before by trailing white space counted in a FILE (`seed.generation`), not in a variable: Playwright starts a new worker after every failed test, a counter that began at 1 again produced a seed byte for byte equal to the one the fake held, and the writes of the test before stayed. That is what happened to the very first visual run, where every test fails for want of a baseline; it would have done the same in CI and given a wrong baseline for the states after "add a member". Fixed here, checked by repeating the run.

Where the "Exchange fake records exactly one add and one remove" is read: the worker is a child of the server, so its calls are not in the call record of the fake tenant. The specs read the effect where the person does (the member list the page and the API show) and the audit log in the database (`support/database.ts`: `lastAuditSeq`, `auditRowsAfter`): one row per member and one summary row, with no name and no address in any row.

## Product findings (nothing silently patched)

1. **Delete of a contact: two 404 requests after the DELETE succeeded.** Once the `DELETE /api/v1/contacts/{id}` is answered, the contact detail page asks `GET /api/v1/contacts/{id}` and `GET /api/v1/contacts/{id}/lists?limit=50` once more, before it leaves for `/contacts`; both answer 404 and the browser logs them as console errors. Nothing is shown to the person, but the e2e `guard` (which fails a test on any unexpected same-origin 4xx) has to allow those two URLs in `contacts.spec.ts` ("delete names the contact..."). Suggested fix: after a successful delete, remove the detail and lists queries from the cache (`removeQueries`) or navigate before invalidating, instead of invalidating them. File: `apps/web/src/features/contacts/queries.ts` (the invalidation of the whole `contacts` key after a write, line about 100, reaches the detail of the contact that was just deleted) and `DeleteContactDialog.tsx` (the navigation after it).
2. **`/groups` page text still says nothing can be changed.** `groups.page.description` (en: "...This page only shows information; nothing can be changed here.") is no longer true since step D1 adds member editing to `/groups/$id`. Dutch has the same sentence. Suggested fix: reword the key in `packages/shared/src/i18n/fragments/groups.{en,nl}.json` (and the unit tests that quote it).
3. **Export is not a route in D1** (P55 is step D2): the Bestuur check for "export" is therefore a 404 today, as in the server test `routes-table.test.ts`, not the 403 plus denial row that US-D4 and SC-D-003 name. `bestuur.spec.ts` pins the 404 with a comment; step D2 must change that assertion to 403 and add `distributionlists.export` to the denial rows.

Also noted, not a defect: the role-pending error appears only when the worker starts (the connect happens once), so a role that becomes effective later is picked up by the next worker start; the specs restart the server to reach that state.
