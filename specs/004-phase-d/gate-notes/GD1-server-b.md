## Decisions and deviations

1. **Route ids of the Exchange routes are lower case** (`distributionlists.list`, not `distributionLists.list`). The id of a route is the `action` of its denial entries and the audit writer's grammar has no capital letter: a denial on `distributionLists.list` ended in a 500. Spec 6.11.1 is amended (all `distributionLists.*` ids, including P46 and P55 of step D2, and a note under the table). The OpenAPI tag stays `distributionLists`. A check reads the spec table and compares method, path, class, audit action and the lower-cased id (`distribution-lists/routes-table.test.ts`).
2. **Step-up above a threshold is decided in the handler.** `PolicyDenied` gained the reason `step_up_required` (`policy/denied.ts`); the wrapper audits it as a denial under the route id and answers 403 `step_up_required`, as for the declared step-up. `directory/step-up.ts` is the one function both write families call.
3. **`validation_failed` carries the code of a custom message** (`http/problem.ts`, `faultCode`). Before, every `custom` issue became the code `custom`, so the codes of `CONTACT_VALIDATION_CODES` (the Zod `message` of the contact schemas, the contract of GD1-0 and what the web form shows) never reached the browser. A message that fits the code grammar (lower case snake case) in a custom issue is now the code; a sentence is still `custom`. Phase B/C tests are green.
4. **`Retry-After` on `exchange_unavailable` (30 s) and `exchange_throttled` (from the hint)** through an optional `retryAfterSeconds` (`http/problem.ts`).
5. **Audit vocabulary kept apart from Phase B.** `audit/actions-d.ts` (seven actions) and `AUDIT_DETAIL_KEYS_D` in `audit/canonical.ts` (nine keys: `memberId`, `result`, `summary`, `total`, `added`, `removed`, `already`, `failed`, `fields`), because `audit-integration.test.ts` and `audit-b-coverage.test.ts` pin 19 actions and 64 keys. No key can hold a name or an address.
6. **A module `groups` beside `directory`** for P53 and P54, so that the Phase C guard "the directory folder has no way to write" (`directory/no-writes.test.ts`) keeps its meaning. `appModules` now has 10 entries (`groups`, `distributionlists`, `contacts` appended). Phase C tests that listed 7 modules or "a write method on `/groups/{id}/members` is 405" were adjusted (named below).
7. **`ExchangeClient.listDistributionGroupMembers` no longer hands out a cut list** (`integrations/exchange/pwsh/pwsh-client.ts`): when the script cut the rows to fit one protocol line it throws `ExchangeUnavailableError('too_many_rows')`; before, the cut was dropped silently. With the 1 MiB line this is about 2,500 members; a list that large is read-only unreadable until the line limit or the projection changes (decision for the owner, AD-02 assumed a few thousand).
8. **`runtime.ts`** is the file `no-undocumented.test.ts` anticipated for the wiring: it holds the `pwsh` command, the default script path (`exchange/worker-script.ps1` next to the bundle, otherwise the source tree), the launcher and the session. `start.ts` and `registry.ts` name no `pwsh`.
9. **Group writes: a group with a hidden membership answers 409 `read_only_object`** (the membership cannot be read, so "already" cannot be decided, FR-C-108). The web already shows no editor for it.
10. **P45 issues no cursor** (the first page is the answer, as the web uses it); a cursor in the request is 400 `cursor_invalid`. `alreadyMember` is `null` when the member read failed. Users without a mailbox address are not offered (EC-D3).
11. **Dynamic lists have no member list.** `Get-DynamicDistributionGroupMember` is not on the frozen allow-list: P42 answers `{ "items": [] }`, the detail has `memberCount: null`, writes and candidates answer 409. The frozen schema has no `state` field for it (unlike the groups members), so nothing tells the UI the list is empty because it cannot be read. A `membersState` (as `MembersResponse`) or the cmdlet on the allow-list is a change to `packages/shared`; reported, not done.
12. **`narrow_search`** is the detail code of the 422 for a result larger than `LIMITS.exchange.listBufferMax` (pointer `/q`). It has no catalogue message yet (the frozen detail codes have `exchange_role_pending` and `exchange_timeout` only): the UI falls back to the generic validation message. A message key in `distributionLists` is the web/shared fix.
13. **P46 (export preview) is a POST rated `read` in the spec**; the route table only allows `write`, `upload`, `auth`, `setup` for a write method. Noted in the spec under the table for step D2.

## The credential source (sub-task 2): stopped, nothing built

The frozen `connect` line wants a PKCS#12 (`pfx-base64` and a password). Two separate things stop a real `ExchangeCredentialSource`:

1. **No PKCS#12 producer.** Phase B generates the certificate with `@peculiar/x509` (`secrets/x509/self-signed.ts`) and seals the PKCS#8 private key (`secrets/secret-store`) plus the public certificate DER (`certificate` table). Node's `crypto` cannot write PKCS#12. `node_modules` holds `@peculiar/asn1-pfx` 2.10.0 (a dependency of `@peculiar/x509`), `asn1js` and `@peculiar/asn1-pkcs9`, but they are transitive; with pnpm's strict layout `apps/server` cannot import them without a line in its `package.json`, which is a new direct dependency (AGENTS.md section 7). Not added.
2. **No way to read the key.** By design (Phase B, FR-B-107) `CertificateHolder` has no member that returns the key, and `SecretsRuntime.state()` exposes only the holder. The only place that decrypts the key is `CertificateService.loadHolder` (`store.open(db, secretId)`), and it zeroes the bytes into the holder. A source needs a new, narrow, audited method such as `withCertificateMaterial(fn)` that hands the PKCS#8 DER and the public DER to a callback and zeroes them after. That is a change to the secrets module and to `secrets/no-plaintext.test.ts`, and a security decision.

Options for the owner:

| | What | Cost / risk |
|---|---|---|
| A | Declare `@peculiar/asn1-pfx` as a direct dependency (already in the lockfile, already in the image through `@peculiar/x509`) and write the PFX with it; encryption of the key bag and the MAC with `node:crypto` (`pbkdf2`, `aes-256-cbc`, `hmac`) | One direct dependency, no new package in the image; about 150 lines; verified by `openssl pkcs12 -info` in CI and by OV-D1 on .NET |
| B | A hand-written minimal PKCS#12 writer (DER by hand, PBES2 AES-256-CBC with PBKDF2-SHA256, HMAC-SHA256 MAC) with no dependency | Hand-written crypto container: review and a test against `openssl` needed; the same two checks as A |
| C | Change the frozen `connect` shape: `certificate: { format: 'pem', certificate: <PEM>, privateKey: <PKCS#8 PEM> }`; the script builds the object with `X509Certificate2.CreateFromPem(cert, key)` (.NET 5 and later; PowerShell 7.6 runs on .NET 9 or later) | An amendment of `packages/shared/src/exchange/protocol.ts` (a frozen file) and `key-handover.ts`, `worker-script.ps1`; no PKCS#12 and no password; U75 (an in-memory certificate on Linux) still decides whether it works; Linux needs the key to be exportable if the module re-reads it (OV-D1) |

Whatever the format, blocker 2 needs the narrow key accessor. **Until a source exists, every Exchange feature answers 503 `exchange_unavailable`** (the registry builds the session lazily; the credential load fails before any process starts; `NO_EXCHANGE_CREDENTIAL`), the process starts and every Graph feature works. The injection point is `ExchangeWorkerSettings.credentials` in `integrations/exchange/runtime.ts`; `start.ts` does not pass one. The e2e topology cannot exercise lists or contacts before this is decided (it also needs a `pwsh` shim on the PATH that runs `test/fakes/fake-tenant/exchange/standin-process.mjs`; the product has no test hook for it, by design).

## What the e2e and docs streams must know (server-side contract)

- **Ids on the wire.** Lists, contacts and groups: the Exchange GUID (groups of Graph: the Entra id). A user: the Entra object id, also as a member of a list (`ExternalDirectoryObjectId`, UNVERIFIED on member rows, OV-D1/OV-D5). A member without it is shown by its Exchange GUID.
- **Routes** (lower-case ids, see decision 1): P40 `distributionlists.list`, P41 `.get`, P42 `.members`, P43 `.members.add`, P44 `.members.remove`, P45 `.search`; P47 `contacts.list`, P48 `.get`, P49 `.create`, P50 `.update`, P51 `.delete`, P52 `.memberships`; P53 `groups.members.add`, P54 `groups.members.remove`. All answers `Cache-Control: no-store`. Writes are class `write`; a denial is audited under the route id.
- **Lists P40.** Prefix search on name, alias and address (Exchange `-like`), `kind`, `order`, cursor (24 characters, valid 600 s for the actor and the query, held in memory). `memberCount` is `null` on rows and counted on the detail (`null` for a dynamic list or a failed read). `managers` is `null` unless the caller sees every user. 422 `validation_failed` `/q` `narrow_search` above 10,000 rows. 503 `exchange_unavailable` (Retry-After 30, detail `exchange_role_pending` or `exchange_timeout`), `exchange_throttled`, `exchange_permission_missing`.
- **Member writes P43/P44.** Body `{ members: [GUID, ...] }`, 1 to 200, unique. Membership is read first; "already" sends no write. Reasons before any call: `not_found`, `mail_disabled` (no mailbox address), `member_type_not_allowed` (a group). After: `permission_missing`, `rejected`, `throttled`, `unavailable`, `timeout`. A throttled or unavailable Exchange stops the rest (they fail with the same reason). If the FIRST write fails for the role, the manager check, or Exchange being down, the whole request is the problem (503) and nothing is claimed. A user is added by mailbox address, a contact by its GUID, `-BypassSecurityGroupManagerCheck` always sent. `readBackPending` is true when a changed member is not (yet) in the member list read after the write, or when that read fails. More than 20 members need a fresh step-up for a user (403 `step_up_required`, audited).
- **Contacts.** Create 201 with `Location`; the `-Name` is `<alias cut to 57>-<6 hex>`; duplicate address or alias is 409 `conflict` `errors[] { pointer: '/externalEmailAddress' | '/alias', code: 'conflict' }` and no id; the scope for a new contact is checked against the proposed display name, alias and address (an id scope never covers it); an update sends and audits only fields that differ (nothing different: 200, no call, no audit) and the result must stay inside the caller's scope (403 otherwise); a synchronised contact is 409 `read_only_object`; delete needs `{ confirmName }` equal to the display name: 422 `/confirmName` `confirm_mismatch` (or `display_name_characters` for a name with padding or control characters), and the answer names the lists the contact was removed from, cut to the lists the caller may see.
- **Groups P53/P54.** Users only (a group id is `member_type_not_allowed`, an unknown id `not_found`); `already` from the direct membership read first (999 per page, at most 50 pages); a 404 on a remove is "already" (U93); 403 from Graph for one member is `permission_missing` (U96). 409 `read_only_object` for dynamic, synchronised, distribution, mail-enabled security, unknown-kind and hidden-membership groups, before any Graph call.
- **Audit.** Per member: action `dl.member.add|remove` or `group.member.add|remove`, target the list or group id, outcome `success` (added, removed, already) or `error` with the reason as `reasonCode`, detail `{ memberId, result }`; then one summary entry `{ summary: true, total, added, removed, already, failed }` (outcome `error` when nothing was done and something failed). A request that fails as a whole writes the summary alone with outcome `error` and the problem code. Entries of what needs no write come first, then one transaction per chunk, then the summary. Contacts: `contact.create|update` with `{ fields: [names] }`, `contact.delete` with `{ removed: <count> }`; no value of a field anywhere.
- **Limits** in `docs/operations.md`: nine rows added (`RATE_EXPORT`, the `exchange.*` rows, `distributionLists.*`, `groupMembers.*`, `contacts.*`).
