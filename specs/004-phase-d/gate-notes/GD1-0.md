## Amendment 1 (D1, 2026-10-13): the `connect` certificate is PEM, not PKCS#12

**Decision (owner-architect, option C of `GD1-server-b.md`, "The credential source").** The frozen `connect` shape carried `certificate: { format: 'pfx-base64', data, password }`. Phase B stores a sealed PKCS#8 key and a public certificate DER, Node cannot write PKCS#12, and a direct dependency for it was refused (AGENTS.md section 7). The shape is now

```
certificate: { format: 'pem', certificate: <X.509 PEM, one CERTIFICATE block>, privateKey: <unencrypted PKCS#8 PEM, one PRIVATE KEY block> }
```

sent in memory over the stdin pipe, never in an argument, the environment or a log. The worker builds the object with `[System.Security.Cryptography.X509Certificates.X509Certificate2]::CreateFromPem(certificate, privateKey)` (Linux, .NET 7 and later; PowerShell 7.6 runs on .NET 9 or later) and passes it to `Connect-ExchangeOnline -Certificate`. No password exists any more.

What changed (and nothing else of the frozen contract):

| File | Change |
|---|---|
| `packages/shared/src/exchange/protocol.ts` | `CertificateSchema`: `format: 'pem'`, `certificate` and `privateKey`, each 64 to 16,384 characters and exactly one PEM block of its label (`CERTIFICATE`, `PRIVATE KEY`; body of base64 lines up to 76 characters, LF or CRLF, optional final line break); strict (no other member); the old `pfx-base64` shape is refused. `LIMITS.exchange.lineMaxBytes` is unchanged (a 4,096-bit key line is about 3.3 KB) |
| `apps/server/src/integrations/exchange/pwsh/key-handover.ts` | `ExchangeCredential` is `{ appId, organization, certificatePem, privateKeyPem }`; `buildConnectLine` builds the new shape. The strings cannot be wiped (the buffer zeroing of the PKCS#12 is gone); the line is built as late as possible and a new credential is read for every worker |
| `worker-script.ps1` | `New-PemCertificate` (`CreateFromPem`), `Connect-InMemory` takes the two PEMs. The `tmpfs` fallback writes the two PEMs to files (mode 0600, `CreateNew`), builds the object with `CreateFromPemFile`, derives the PKCS#12 file that `-CertificateFilePath` wants (random password that exists only in the function, mode 0600), connects, and removes all three files in a `finally` block. The generated block (allow-list and projections, hashes) is unchanged |
| `apps/server/test/fakes/fake-tenant/exchange/{worker-standin.ts,standin-process.mjs}` | the stand-in reads the new shape; in `tmpfs` mode it plays the three files |
| `packages/shared/test/exchange-protocol.test.ts`, `apps/server/test/exchange/{no-key-on-disk,allow-list,real-pwsh}.test.ts`, `support.ts` | new shape; canary PEMs; the retired route is gone from the script (asserted) |

**Behind the shape (also D1):** `SecretsRuntime.withCertificateMaterial(purpose, fn)` is the one audited accessor that hands the PEMs to a callback and revokes them afterwards (`secrets/state.ts`, `certificate-service.ts#withMaterial`, `certificate-material.ts`); `integrations/exchange/pwsh/credential-source.ts` (re-exported by `integrations/registry.ts`, the one place `start.ts` may import it from) is the real `ExchangeCredentialSource` on top of it; `start.ts` passes it as `ExchangeWorkerSettings.credentials`. The access is a log line (`certificate_material_access`: purpose and thumbprint), not a database audit entry: a new audit action would change the audit table of the Phase B spec (`audit-integration.test.ts` compares it row by row). A degraded secrets state, no certificate, no key that opens it, or no initial domain answers 503 `exchange_unavailable` (reason `credential_unavailable`); every Graph feature keeps working. The organization is `tenant_connection.initial_domain` (the `isInitial` domain the wizard stored).

**Proof and what is NOT proven.**
- Proven in CI with no tenant: the schema and its negatives; the PEMs are the certificate and the key that belong together (`X509Certificate.checkPrivateKey`) and match what the factory generated; no key material in errors, logs, audit rows or files (canary scans, `secrets/no-plaintext.test.ts`, `secrets/certificate-material.test.ts`); the accessor is named only in the allowed files (`secrets/material-scope.test.ts`).
- Proven only where `pwsh` exists (`real-pwsh.test.ts`, skipped otherwise; **it was not run when this was written: the build container has no `pwsh`**): `CreateFromPem` on a certificate and key made by the product's own factory (RSA, PKCS#8), that the key signs for the certificate, the tmpfs files with mode 0600 and their removal also on a failed connect.
- **UNVERIFIED (OV-D1, U75):** that `Connect-ExchangeOnline -Certificate` accepts a `CreateFromPem` object on Linux, that the module does not need an exportable key, and that PowerShell binds a `string` to the `ReadOnlySpan<char>` parameters of `CreateFromPem` (it should, through the implicit conversion; `real-pwsh.test.ts` proves exactly this call where `pwsh` exists). If the first fails, the `tmpfs` fallback is the answer and is already adapted. The owner procedure `docs/owner-test-phase-d1.md` still builds a `pfx-base64` connect line and must be rewritten for PEM (not part of this change).

**New in the same step.** `narrow_search` has its catalogue message (`distributionLists.error.narrow_search`, and the contacts wording `contacts.error.narrow_search`, both languages). The product looks `pwsh` up on the PATH of the server process (`resolveCommand`, `runtime.ts`), because the worker is started with an environment without a PATH, which would otherwise ignore the PATH of the server; this is what lets the e2e shim (`e2e/support/pwsh-shim/`, README there) stand in for PowerShell without a test hook.


## Amendment 2 (D1, 2026-10-13): an optional `aadsts` number on a refused connect

**Decision.** The error object of an answer may carry one more optional member, `aadsts`: an integer 1 to 9,999,999, the number of an Entra `AADSTS<n>` code that the sign-in service gave when `Connect-ExchangeOnline` was refused. It is digits only, parsed by the worker from the error and never the text around it, so FR-D-107 (no free text) holds. Backwards compatible: every answer of Amendment 1 and earlier is still valid, a reader that does not know the member sees a strict-object failure only if it is an old build of this same schema (server and worker ship in one image).

**Why.** A production deployment (0.3.63) showed "Exchange Online is not available" on Contacts and Distribution lists and the log could not say why. The reproduction in a real PowerShell 7.6.6 with module 3.10.1 showed two faults: the server could not start the worker at all (the command `pwsh` was not on the PATH of the image, see the fix in `runtime.ts`), and a refused connect (a wrong application or a missing consent, AADSTS700016 and similar) was answered as `not_found`, because the English text of the error contains "was not found", and the session turned that into `worker_start_failed`. A connect refused with an `AADSTS` number is now `permission_denied` plus `aadsts`; the session logs it (`exchange_worker`, `reason: 'connect_refused'`, `code`, `aadsts`).

| File | Change |
|---|---|
| `packages/shared/src/exchange/protocol.ts` | `aadsts` optional on the error object of `ExchangeResponseSchema` |
| `packages/shared/test/exchange-protocol.test.ts` | accepts the number, refuses text, zero, fractions and 10,000,000 |
| `worker-script.ps1`, `session.ts` | the worker sends it; the session logs it |

The generated allow-list and projection hashes are unaffected (they cover the cmdlet table, not the protocol schema).

## Amendment 3 (D1, 2026-10-13): an optional `detail` on an error (type name and error id)

**Decision.** The error object of an answer may carry one more optional member, `detail`: an object with the optional strings `type` (the .NET type name of the innermost exception) and `errorId` (the first part of `FullyQualifiedErrorId`), each only letters, digits, dots and underscores, 1 to 120 characters, filtered in the worker and checked again by the schema. Never message text, so FR-D-107 holds. Backwards compatible.

**Why.** On 0.3.64 the owner's tenant connected (the first call took about 4 s and nothing was refused) but every Contacts and Distribution lists call answered 503 and the log did not say why. The server now logs one `exchange_fault` warning per failed call (`result`, `errorType`, `errorId`), and `connect_refused` carries the same two fields.

## Amendment 4 (D1, 2026-10-13): `detail.hints`, words of a closed list found in an error

**Decision.** `detail` may carry `hints`: up to 16 strings of `[a-z0-9_]`, each either a word of a fixed vocabulary in the worker (role, permission, unauthorized, parameter, proxy, ...) that the error text contains, or `http_<400-599>`. The words come from the list, never from the text, so FR-D-107 holds.

**Why.** On 0.3.65 the connect succeeds and every cmdlet answers `internal` with `WriteErrorException` (the module reports its error with `Write-Error`); the type name alone does not say what failed. The hints tell a role or consent problem from a parameter or proxy problem without sending text.

## Amendment 5 (D1, 2026-10-13): `detail.text` and `detail.textLength`, an OPT-IN diagnostic exception to FR-D-107

**Decision (owner, 2026-10-13, answer "Ja, opt-in en gemaskeerd").** `detail` may carry two more optional members: `text` (a string of at most 300 characters) and `textLength` (an integer 0 to 100,000, the length of the UNMASKED outer message, so an empty message is visible). They are sent **only** when the server started the worker with `EXCHANGE_DEBUG_ERRORTEXT=1` in the worker's environment, which the server does only when the operator set the variable `EXCHANGE_DEBUG_ERRORTEXT=1` (default off; any other non-empty value other than `0` refuses the start). In the default mode neither member is ever sent, the worker never sends free text and FR-D-107 holds without exception.

**This is an explicit, documented exception to FR-D-107.** It is opt-in, masked, truncated, temporary and for the owner's own server log only:
- *Opt-in:* off unless the variable is `1`; a startup warning (`{ event: 'exchange_debug_errortext', enabled: true }`) makes it visible in the log while it is on.
- *Masked:* the text is the message of the outermost exception and, if different, of the innermost one, joined with ` | `. In the worker, before it leaves the process: e-mail addresses become `X`, GUIDs become `X`, runs of 20 or more characters from `[A-Za-z0-9+/=_-]` become `X`, whitespace and control characters collapse to one space.
- *Truncated:* at most 300 characters after masking.
- *Temporary:* meant for one troubleshooting session; the operator removes the variable afterwards. It is not a feature of the product and no screen, API answer, audit row or error page carries the text: only `exchange_fault` and `connect_refused` log entries (`errorText`, `errorTextLength`, `null` when absent).
- *Own log:* the masking is a pattern, not a proof: a display name or a tenant name in the message is NOT masked. The owner reads the log output before sharing it with anyone.

**Why.** On 0.3.66 the connect succeeds and every cmdlet (`Get-MailContact`, `Get-DistributionGroup`) answers `internal` with `detail.type` and `errorId` both `Microsoft.PowerShell.Commands.WriteErrorException` (the module reports its error with `Write-Error`) and an empty `hints` list, so the message matches none of the closed vocabulary of Amendment 4. Only the text can tell what the module complains about.

| `packages/shared/src/exchange/protocol.ts` | `text` and `textLength` optional on `detail` |
| `worker-script.ps1` | `Get-MaskedErrorText`, `Get-DebugErrorText`; `Send-Failure -Record` adds both only when `$env:EXCHANGE_DEBUG_ERRORTEXT -eq '1'` |
| `worker-launcher.ts`, `runtime.ts`, `start.ts`, `config/env.ts` | the variable, the field `exchangeDebugErrorText`, and the single place the worker gets `EXCHANGE_DEBUG_ERRORTEXT=1` in its otherwise minimal environment |

## Amendment 6 (D1, 2026-10-13): `detail.probes`, five small reads after the first failure (opt-in)

**Decision.** With `EXCHANGE_DEBUG_ERRORTEXT=1` only, the worker runs once per process, after its first failed call, five small reads (`Get-OrganizationConfig`, `Get-Recipient -ResultSize 1`, `Get-DistributionGroup -ResultSize 1`, `Get-MailContact -ResultSize 1`, `Get-MailContact`) and returns `detail.probes`: fixed words only (`org_onms` or `org_other`, then `orgcfg_ok`, `recip_fail`, `contact1_missing`, ...). The words are ours; no text of any answer is read into them.

**Why.** On 0.3.67 the error text is Exchange's generic "server side error" for every call, with the connect, the consent and the Exchange Administrator role all in place. The probes tell a tenant, token or role problem (all fail) from a problem of one call shape (a parameter such as `ResultSize`).
